Agent timelines

Agent timelines

An agent timeline records explicit project work: stable task IDs, weighted progress, authored reports, discussions and cooperative control receipts. It is separate from the Markdown checkbox Tasks timeline. Moving a checkbox line does not move or rename an agent task. An optional note_id links a project to a note in the same vault without modifying that note. The Web client currently rejects note IDs above JavaScript’s safe-integer range rather than rounding them or saving a changed link. Use the exact-integer CLI for those projects; do not clear the link merely to make an edit succeed. A future lossless Web wire format is needed to support the full int64 range in that client.

Back to track. See CLI for vault selection.

Normal Claude and Codex sessions

Use timeline-session for a simpler, opt-in workflow without piping the agent's stdout. Select an existing vault and explicit project before writing:

export TRACK_VAULT=/absolute/path/to/vault
export TRACK_TIMELINE_PROJECT=demo
track timeline-session init --title 'Demo project'
track timeline-session start --agent codex --session stable-session-label
# Use the returned run ID below, not the literal placeholder.
track timeline-session task --run RUN --task implement --title 'Implement feature' --status active
track timeline-session task --run RUN --task implement --done 15 --remaining 10
track timeline-session show
track timeline-session report --run RUN --event milestone-1 --summary 'Focused tests passed'

Choose --agent claude for Claude. Keep the session label/run across resume and compaction; choose a new label for an independent or forked session. Task IDs are local to that run. Updates preserve omitted fields, including title and effort. Use --parent for hierarchy, --detail for explicit context, and --status done only after verifying the outcome. A repeated identical task update does not add an event. On revision conflict, reread and reconcile before retrying. Reports require a stable --event: repeat it only with identical summary/uncertainty.

The repository's session integration guide contains a shared skill, persistent project-instruction template, and Claude/Codex SessionStart command-hook examples. After one-time reviewed setup, the startup policy asks the agent to track substantive work automatically; no per-conversation Timeline request or skill invocation is needed. Without a successful hook context, automatic tracking skips instead of asking for a label. Installation is manual and requires reviewing the destination and client permissions; no settings are changed by Track. The hook requires TRACK_TIMELINE_ENABLED=1, obtains a stable run from the client session ID, and restores context after resume/compact. It ignores transcript paths and prompts. Without opt-in it does nothing; failures do not block normal work. Disable the hook with TRACK_TIMELINE_ENABLED=0; explicit CLI writes remain available.

Skills ask the agent to write meaningful milestones, not every tool call. They cannot guarantee model compliance. Stop/End never completes tasks automatically. Only deliberately supplied text is saved; it is not automatically redacted. Do not submit credentials, private transcripts, or sensitive user data. Reports are optional authored summaries, not timers or extra model calls. Client hook and skill support must be checked on the installed version; live interactive Claude/Codex integration has not been verified by the fixture tests.

Start a project

Select the intended vault before writing. Every apply command reads one JSON request from stdin:

track timeline-project apply --id demo <<'JSON'
{"source":"example","event_id":"create-demo","expected_revision":0,"kind":"project.create","payload":{"title":"Demo project","mode":"serial"}}
JSON

track timeline-project apply --id demo <<'JSON'
{"source":"example","event_id":"add-task","expected_revision":1,"kind":"task.upsert","payload":{"id":"implement","title":"Implement the feature","status":"active","owner":"example","weight":1,"done_minutes":15,"remaining_minutes":45,"mode":"serial"}}
JSON

track timeline-project list
track timeline-project get --id demo

project.update and task.upsert accept complete replacement records, not partial patches. Read the current snapshot before editing. Tasks may specify parent_id, detail, and priority (P0–P3 as integers 0–3). The parent must already exist, and cycles are refused. IDs contain ASCII letters, digits, hyphens and underscores, start with a letter or digit, and are at most 96 characters.

Task states are pending, active, paused, blocked, done, and retired. Children determine a parent's calculated progress, so parent effort is not counted twice. Leaves use done_minutes / (done_minutes + remaining_minutes); done leaves are complete. Sibling fractions are weighted; omitted or zero weight means one. Retired subtrees are excluded from progress. The snapshot includes task_progress for each task’s own subtree, using the same formula as the project total. Retired subtrees contribute no completion or effort to their ancestors; individual descendants remain inspectable in their own projections. Counts retain explicit task statuses even when a subtree is excluded. Remaining estimates sum in serial groups and take the maximum in parallel groups. They are estimates, not a promise about elapsed wall time or actual agent scheduling.

Reports and discussion

Use report.add with a unique id, author, RFC3339 period_start/period_end, summary, and nonempty event_sequences referencing existing events. Optional task_id, uncertainty, and user_action retain the distinctions between progress, unresolved questions and required decisions. Reports are explicitly supplied text: Track does not call a model or collect a transcript.

Use discussion.add with id, author, text, target_type (project, task, or report), and the corresponding target_id. Reports and discussion entries are append-only; existing IDs cannot be overwritten. Submit a new entry to correct or follow up on earlier text.

Cooperative control, not process control

control.request records id, task_id, the task's owner, action (pause or resume), and status: "requested". The responsible integration can send control.update with id, status and result. Allowed receipts are acknowledged, completed, rejected, and failed; completion requires acknowledgement first. A receipt's request source must match the routed owner.

Track does not launch, message, stop or resume a process. A request does not change task status, and a completion receipt is the integration's report, not independent verification. Source/owner labels are routing and provenance, not authentication. The local CLI and existing protected loopback Web API remain the trust boundary; do not expose them as a remote agent service.

Conflicts and retries

Every request has source, event_id, expected_revision, kind, and payload. Use a fresh source/event identity for each new action. A stale revision fails rather than overwriting another writer. Read the newer snapshot and review the intended change before sending a new action.

If a response was lost, resend the identical request with the same source/event identity. It is applied at most once, even when the expected revision is now old. Reusing that identity for different content fails. Never generate a new event ID merely because a write timed out.

Recorded state and interrupted workers

Task states are the latest submitted records, not process heartbeats. A successful refresh confirms that Track was read; it does not confirm that the responsible worker is still alive. An active task may remain after an importer is killed or rejects malformed input.

Before correcting an interrupted run, stop or confirm the end of its writer outside Track. Inspect its latest events and reports, then edit the complete task record through the Web or Neovim view with the current revision. Use blocked when the outcome is unknown; do not mark it done without evidence. Preserve its ID, parent, owner and other fields. Correct each affected child as well as the execution parent, because parent progress is calculated from children. A concurrent revision change requires another review, not a blind retry. Add an authored discussion explaining the correction if useful, without including private transcript contents.

This correction records your assessment; it does not stop a process. The Codex importer refuses new writes over a task edited outside its run. Start any later invocation with a new run ID rather than treating a manual correction as permission to resume the old stream.

API and storage

  • GET /api/timeline/projects lists projects.
  • GET /api/timeline/project?id=demo reads one snapshot.
  • POST /api/timeline/project?id=demo accepts the same explicit request as the CLI.
  • Use the normal vault query selector and local Web write protections.

Versioned event journals live in .track/timelines/<project-id>.json; snapshots are reconstructed from those records, not a disposable index. Back them up with the vault. Standard static publication does not export them. No automatic conversation, credentials, environment, or shell-history capture is performed. Content submitted explicitly is retained locally, so do not submit secrets.

Linux and macOS are supported. Cross-process writers use a bounded lock and atomic replacement; corrupt or unsupported files fail without being reset. A project is limited to 1,000 tasks, 10,000 events and an 8 MiB journal; each payload is limited to 64 KiB. Limits reject writes instead of silently deleting history. Rotation, selective retention and automatic agent adapters are not provided; a new project can be started explicitly when needed.

Web and Neovim views

In the live Web workspace, choose Agent timeline in the navigation rail or mobile dock. Create or select a project, then use Edit project, task titles, Add authored report, Add discussion, or Request pause or resume. Recorded events shows source records. These are explicit actions, not background agent dispatch. Unsaved form edits remain separate from polling results. Revision conflicts require review and explicit retry; uncertain network retries keep their original event identity. Static published sites do not provide this workspace.

In Neovim, run :Track timeline to choose or create a project, or :Track timeline demo to open one. The ordinary Neovim split shows tasks, estimates, reports, discussions, receipts and events. The split refreshes every five seconds while open, without overlapping pending writes. Press r to refresh immediately, a to prepare an explicit record, and q to close. The record opens as a JSON draft: edit its payload and :write to submit, or :bd! to discard without sending. For task.upsert, choose a new task or select an existing task to prefill its complete saved record. The draft keeps the revision captured with that record; later polling cannot silently rebase it. Drafts are locked during submission; a write receipt never silently discards newer edits. Closing a view does not cancel an already submitted write. There is no interactive terminal TUI.

For a custom Neovim or komado presentation:

local view = require('track.agent_timeline').new('demo', { vault = 'work' })
view.refresh(function(err)
  if err then vim.notify(err, vim.log.levels.WARN) end
end)
local stop = view.watch(5000)
-- Call view.dispose() when your owning UI is removed (or stop() to stop polling only).
-- Add view.komado_component() to your existing komado root.
-- Or read view.rows() / view.snapshot from another cached provider.

The adapter emits User TrackTimelineChanged after results. Rendering does not run a subprocess; custom monitoring is opt-in and lifecycle-owned, and stale data is marked after a failed read. The compact component includes recent reports, discussion and control receipts as well as task/subtree progress; open :Track timeline for full history and event payloads. The component uses komado's existing API without requiring it for other views. view.request(kind, payload) prepares an idempotent request; view.apply(request, callback) submits it once. Keep that request for an uncertain retry, and do not refresh during an outstanding write. The default :Track timeline view uses the configured vault; custom adapters can pass a named vault or vault_dir.

Connecting an external worker

Track supplies a recording protocol, not an agent runner. An external worker can opt in by submitting progress and authored reports through timeline-project apply and polling get for control requests addressed to its task and owner. Acknowledge accepted requests, then record completion only after reaching the corresponding safe state. Continue polling while paused. A crash may leave an acknowledged request incomplete; reconcile it explicitly instead of assuming that the earlier process completed it. Use a distinct owner label per worker.

The repository's examples/timeline-worker/ contains an executable Python-standard-library reference adapter and disposable-vault instructions. It performs finite sleep-only steps, records a report with event references and demonstrates actual safe-point pause/resume. It never starts another agent, invokes a model, runs supplied commands or collects private context. After a definite revision rejection, the example retries at most three times only when its affected task, controls and report evidence are unchanged. Actual target changes stop visibly; uncertain timeouts retain the identical request rather than rebasing. Existing tasks are not taken over; use a new task ID for each demonstration.

Local offline snapshot

track timeline-project get --id demo > timeline.json writes a self-contained read snapshot including recorded events, task/subtree projections, reports and discussion. Choose a private local destination: this explicit export contains the records you submitted and is not redacted. It is useful for offline inspection, but is not a restore command. Use the ordinary vault backup for authoritative recovery. Static site publication still excludes timeline journals.

Codex CLI event integration

The repository's examples/codex-timeline/ adapter connects an explicitly piped codex exec --json invocation to an existing Track project. It reads standard input; it does not start Codex, read session files, call a model or contact a remote service. The required vault, project, owner and run ID make the destination and provenance explicit. Use a new run ID for a different invocation; replay only the same stream with the same ID.

The default allowlist records turn lifecycle, fixed item-type/status counts and plan completion counts. It excludes prompts, agent messages, reasoning, commands, file paths, tool names/output and upstream error text. Plan steps do not have stable IDs in this event API, so the adapter does not invent persistent identities for individual steps or copy their text. Recorded progress means observed lifecycle, not a time estimate or proof that the agent's work is correct. Non-fatal warning items are ignored even before a turn starts; declined commands are counted as declined, not as completed work. If independent writers exhaust the bounded conflict retries, wait for contention to settle and replay the identical stream with the same owner and run ID. Actual edits to the affected records still require explicit reconciliation.

This event stream is one-way. It cannot pause or resume Codex, and never acknowledges a control request as if it could. An interrupted or failed stream does not produce a successful completion. See the adapter README for the verified event schema, limits and pipeline setup. The integration is tested with documented event fixtures and the actual Track executable; a live model/account session is a separate operational check, not something Track runs automatically.
